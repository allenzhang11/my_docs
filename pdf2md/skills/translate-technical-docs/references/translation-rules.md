## 核心检查顺序

翻译每个句子时按以下顺序确认，不要先追求中文流畅：

1. 找出主语、谓语、宾语和动作承受者。
2. 找出条件、时间、范围、例外和否定。
3. 判断情态动词表示能力、许可、可能性、建议还是强制。
4. 确认代词、省略成分和跨句指代。
5. 调整中文语序，并检查是否仍表达同一技术关系。

优先保留以下信息，任何一项都不能因改写而丢失：

- 否定词，例如 `not`、`never`、`without`、`neither`。
- 限定词，例如 `only`、`unless`、`except`、`at least`、`at most`。
- 频率和程度，例如 `always`、`usually`、`may`、`can`、`typically`。
- 条件和顺序，例如 `if`、`when`、`before`、`after`、`until`。
- 责任主体和动作对象，尤其是被动句、`by` 短语和 `allow / enable` 结构。
- 版本、平台、单位、默认值、弃用状态和兼容性范围。

## 情态动词与约束词

把情态动词译成固定强度，但必须结合上下文判断。下表是默认映射，不是脱离上下文的机械替换。

| 英文 | 默认译法 | 注意 |
| --- | --- | --- |
| `must` / `shall` | 必须 | 规范中的强制要求 |
| `must not` / `shall not` | 不得 / 禁止 | 不要弱化成“不建议” |
| `required` | 必需的 / 必须 | 区分“必需项”和“必须执行” |
| `should` | 应 / 应当 | 通常是建议或规范性推荐，不是绝对强制 |
| `should not` | 不应 | 不要译成“不能” |
| `may` | 可能 / 可以 | 表示可能性时译“可能”，表示许可时译“可以” |
| `can` | 能够 / 可以 | 表示能力或客观可行性 |
| `cannot` | 不能 | 不要与“可能不”混淆 |
| `could` | 可能 / 能够 | 结合虚拟语气和过去时判断 |
| `will` | 将 / 会 | 不要仅凭该词判定必然发生 |
| `would` | 会 / 将 | 注意条件句和假设语气 |
| `might` | 可能 | 通常比 `may` 更不确定 |
| `need not` | 不必 | 不是“不得” |
| `optional` | 可选的 | 不要译成“可选但推荐” |

常见限定结构的默认处理：

| 英文 | 中文 | 要求 |
| --- | --- | --- |
| `only if` | 仅当……时 | 保留充分条件和限制 |
| `if and only if` | 当且仅当 | 不要省略双向条件 |
| `unless` | 除非 | 不要把否定关系翻转 |
| `except when` | 除……情况外 | 保留例外范围 |
| `at least` / `at most` | 至少 / 至多 | 保留边界含义 |
| `up to` | 最多 / 至多 | 结合单位判断是否含上界 |
| `not necessarily` | 不一定 | 不要译成“不会” |
| `by default` | 默认 | 不要误译成“通过默认方式” |
| `deprecated` | 已弃用 | 不要译成“已删除” |
| `experimental` | 实验性的 | 不要译成“稳定版” |

## 长句与逻辑关系

处理长句时先拆出主干，再挂回修饰成分：

```text
When A occurs, B must do C before D, unless E is configured.
```

可拆成：

```text
当 A 发生时，B 必须在 D 之前执行 C；除非已配置 E。
```

不会丢失的条件包括：

- `when A occurs` 是触发条件。
- `must` 是强制要求。
- `before D` 规定执行顺序。
- `unless E` 是例外条件。

拆分长句时遵守以下规则：

- 用句号拆句后，下一句应保留必要主语，避免“它”指代不清。
- 条件从句可以前置或后置，但条件不得变成结果。
- 英文分词结构可展开成短句，但不得补写原文没有的因果关系。
- 并列项的层级用中文序号或分号表达清楚，不要合并成含糊的一段。
- 比较级和最高级要保留比较对象，例如 `faster than TCP` 是“比 TCP 快”，不是笼统的“很快”。

被动句只有在动作执行者明确时才改为主动句。例如：

```text
The participant is created by the DomainParticipantFactory.
```

应译成“DomainParticipantFactory 创建 participant”，不能译成没有主体的“participant 被创建”。

## 术语与专有名词

- 第一次出现时使用“中文（English）”，后续沿用同一译法；代码中的标识符保留英文。
- 产品名、协议名、API 名、类型名、枚举值、消息字段和配置键默认不翻译。
- 缩写首次出现时给出英文全称和中文解释，但不要对每个缩写反复展开。
- 同一文档中不要轮换使用多个近义译法，例如把 `endpoint` 同时译成“端点”“终端”和“节点”。
- 原文故意区分大小写时保留大小写，例如 `DDS`、`Fast DDS`、`DataWriter`。
- 术语翻译不确定时，采用业界常见译法并加一条简短译注。
- 不要根据常识补充原文没有的版本行为；版本差异只能标记为待确认。

代码注释默认保持原样。若必须让初级读者理解注释的含义，在代码块外解释，不改写代码块内容。

## Markdown 与 PDF 提取文本

### Markdown 结构

- 保持标题层级和标题顺序。译文可改标题文字，但不擅自升降级。
- 保持无序列表、有序列表、任务列表和嵌套层级。
- 保持表格的列、行、表头和单元格对应关系；表头缩写可在表内首次解释。
- 保持引用块、提示框、脚注和交叉引用。
- 保持链接目标、图片路径和锚点不变；可翻译链接文字与图片 alt 文本。
- 保持代码围栏语言标记和代码内容不变。
- 保持行内代码内容不变；必要时在行内代码外解释。
- 不把多个列表项合并成段落，也不把警告混入普通正文。

### PDF 提取结果

PDF 转 Markdown 后常见以下问题，应按证据谨慎清理：

- 删除重复页眉、页脚和页码，但保留正文中的页码引用。
- 合并被版面拆开的单词和句子，但不要误合并代码、表格或列表项。
- 修复因行尾连字符产生的错误断词；代码和 URL 中的连字符要原样保留。
- 目录只保留一次，并确认目录页码没有混入正文标题。
- 图片、公式和表格若提取缺失，明确标记缺失，不能用推测内容补齐。
- 代码缩进、空格和符号属于技术信息，优先保持，不做“格式美化”。

## 双语对照与学习版

### 双语对照

以段落、列表项或表格行为最小对齐单位：

```markdown
The participant must be enabled before creating a DataWriter.

在创建 DataWriter 之前，必须先启用 participant。
```

代码块、表格和图片通常只保留一份，并在相邻位置提供译文说明。原文与译文的顺序应保持一致。

### 学习版

学习版仍以完整忠实译文为主体。附加内容只包括：

- 章节开头的 `本节速览（非原文）`。
- 首次出现术语的简短解释。
- 容易误解处的 `译注`。
- 文末术语对照表。

速览和译注不得替代正文。不要把每个普通句子都改写成教程，也不要增加原文没有的最佳实践。

## 交付前检查

逐段回查以下项目：

| 类别 | 检查问题 |
| --- | --- |
| 语义 | 是否改变主语、动作、对象、因果或条件？ |
| 强度 | `must / should / may / can` 是否保持原强度？ |
| 完整性 | 段落、列表项、表格单元格、警告和脚注是否齐全？ |
| 标识符 | 代码、命令、路径、URL、版本和 API 名是否原样保留？ |
| 一致性 | 同一术语是否全篇使用同一译法？ |
| 可读性 | 代词是否清楚，长句拆分后逻辑是否仍然完整？ |
| 标注 | 速览和译注是否明确标为非原文？ |
| 不确定性 | 是否把猜测写成了确定事实？ |

Markdown 文件至少运行一次结构检查脚本。脚本通过只表示关键结构没有明显丢失，仍须人工核对语义。
